# Runesgalder threat model

- Version: 0.1
- Date: 2026-11-23
- Status: Living document; v0.1 pre-alpha
- Scope: Flow runtime, Sandbox contracts, planned Linux sandbox daemon, MCP server, build and release pipeline

## 1. Purpose

This document describes the assets, trust boundaries, threats, mitigations, and residual risks for Runesgalder. It exists to keep security claims honest. A feature is not a security control until it is implemented, tested, and documented.

The central assumption is that AI-generated code and model output are untrusted. The central goal is to make every effect governed, visible, and bounded.

## 2. Scope and non-goals

In scope:

- Untrusted C# generated by a model or supplied by a user.
- The compile pipeline, worker lifecycle, sandbox policy, and host data contract.
- The Flow journal, policy, approvals, artefacts, and event stream.
- The MCP server boundary.
- Build, dependency, and release integrity.
- Secret handling and telemetry defaults.

Out of scope for v0.1:

- Hardened multi-tenant isolation.
- Protection from a compromised host kernel, hypervisor, container runtime, or CI platform.
- Malware detection or antivirus behaviour; isolation is the control, not detection.
- Elimination of all covert channels.
- Protection from a malicious project operator who intentionally weakens policy.
- Windows native strong isolation. This is deferred.

## 3. Assets

- Host files, environment variables, and credentials.
- Model provider credentials and tool credentials.
- User data supplied to a run, including CSV files and prompts.
- The integrity of generated code, compiled assemblies, and cached artefacts.
- The journal, run history, approvals, and audit evidence.
- The artifact store and generated outputs.
- CPU, memory, disk, file descriptors, process table, and network capacity.
- The package supply chain, CI credentials, signing identities, and release artefacts.
- The trust of users who rely on the project's security claims.

## 4. Trust boundaries

1. **Host application to Flow runtime.** The host is trusted. The runtime must not let untrusted inputs silently become host capabilities.
2. **Model output to typed code.** Model output is untrusted. It becomes code only through a compile-and-policy pipeline.
3. **Compile pipeline to worker.** The compiled assembly is untrusted. The worker must run outside the control-plane process.
4. **Worker to host contract.** The worker receives only narrow, host-defined interfaces such as `ITable` and `IScriptContext`.
5. **Container to host kernel.** The container boundary is the main v0.1 isolation boundary and is not absolute.
6. **MCP client to server.** The MCP server is a capability boundary; tool calls must be authenticated and policy-checked.
7. **CI and release pipeline to package registry.** Build and signing credentials are high-value assets.

## 5. Assumptions

- The host operating system, kernel, container runtime, and hardware are patched and trustworthy.
- The operator configures the host and does not intentionally disable isolation.
- v0.1 is local and single-tenant. It is not a multi-tenant service.
- Generated code is malicious by default, even when the prompt appears benign.
- Prompt injection is expected. Policy and isolation are the last line of defence, not model behaviour.
- No secret is intentionally passed into generated code, the prompt, the journal, or telemetry.
- Network access is denied unless an explicit policy allows it.
- Security claims must name the isolation tier and the assumptions behind it.

## 6. Threats and mitigations

| ID | Threat | Impact | v0.1 mitigation | Residual risk |
| --- | --- | --- | --- | --- |
| T1 | Sandbox escape through a kernel, container runtime, or misconfiguration | Host compromise, data loss, lateral movement | Rootless container, user namespaces, cgroups v2, seccomp, Landlock where available, read-only root filesystem, no Docker socket, no-new-privileges, dropped capabilities, narrow host interface | Kernel and runtime vulnerabilities remain possible; container isolation is not a hard security boundary against a determined attacker |
| T2 | Arbitrary host filesystem access | Data theft, tampering, persistence | Generated code receives `ITable` and `IScriptContext`, not host paths; read-only virtual inputs; scratch quotas; path validation rejects rooted and traversal paths; no host home directory mount | Bugs in host contracts or mounts can expose data; operator-added mounts widen the boundary |
| T3 | Network egress or data exfiltration | Data loss, command and control, abuse of third-party services | Network denied by default; no DNS or metadata-service access; egress broker with allowlists and credential injection is the planned opt-in path | Covert channels and allowed destinations can still carry data; operator-enabled network widens risk |
| T4 | Resource exhaustion or denial of service | Host instability, cost, starvation of other work | CPU, memory, wall-clock, process, file-descriptor, and output limits; per-run scratch quotas; cancellation | Limits can be mis-sized; a single-tenant host can still be saturated by allowed work |
| T5 | Banned APIs inside generated code | Escape attempts, host manipulation, reflection abuse | Host-defined contract assemblies; banned-symbol analysis; no P/Invoke, unsafe blocks, process spawn, `Assembly.Load`, dynamic code, or arbitrary NuGet restore; structured diagnostics | Roslyn, runtime, or analyzer bugs; new .NET APIs may create bypasses |
| T6 | Host contract abuse or confused deputy | Access to data the run should not see; unexpected capabilities | Narrow interfaces; no ambient authority; per-run table views; output quotas; host-side validation | A contract method with too much power can be abused; contract changes need security review |
| T7 | Prompt injection or model/tool misuse | Unsafe tool calls, data leakage, incorrect actions | Every effect is an effect; policy checks before model, tool, and code execution; approvals for sensitive effects; allowlists; typed contracts | The model can still be manipulated within allowed capabilities; policy is the boundary, not the prompt |
| T8 | Secret leakage through prompts, logs, traces, exceptions, or artefacts | Credential theft, account compromise | Secrets injected by the host at the boundary; generated code never receives them; prompt/completion capture off by default; redaction; local-only default | Bugs in redaction or host code can still leak; operator logs may contain sensitive data |
| T9 | Journal or artefact tampering | False audit trail, poisoned results | Append-only journal; content-addressed artefacts; per-run correlation; future signing and attestations | A local attacker with write access to the store can still tamper; signatures are not yet implemented |
| T10 | Supply-chain compromise | Malicious dependency, build, or release | Central package management; pinned SDK; CodeQL; Dependabot; minimal dependencies; release signing and attestations planned | Upstream compromise remains possible; signing reduces but does not eliminate risk |
| T11 | MCP tool abuse | Unauthorised code execution, data access, or cost | Per-tool policy; input validation; timeouts; bounded outputs; local stdio first; authentication for remote transports later | A local MCP client with access can still invoke allowed tools; transport security is future work |
| T12 | Compile-pipeline denial of service | CPU/memory exhaustion before isolation | Source-size limits; reference allowlists; compilation timeouts; bounded diagnostics; no arbitrary analyzers; worker isolation | Roslyn itself can be expensive on adversarial input |
| T13 | Artifact cache poisoning | Wrong code executed, data corruption | Content-addressed keys; source and reference hashes; provenance metadata; cache validation | A compromised cache or hash collision scenario is residual risk |
| T14 | Information leakage through errors or timing | Inference of host data or secrets | Structured errors; no host paths or secrets in generated-code diagnostics; bounded output; conservative logging | Covert channels and timing side channels are not eliminated |

## 7. Controls that must exist before any strong claim

The project should not make a strong isolation claim until all of the following are implemented and tested:

- The Linux worker actually runs outside the control-plane process.
- The container is rootless and uses user namespaces, cgroups v2, seccomp, and a read-only root filesystem.
- Network is denied by default and verified by tests.
- Banned-symbol analysis rejects P/Invoke, unsafe code, process creation, `Assembly.Load`, and dynamic code.
- The worker receives only host-defined contracts and a per-run table view.
- Resource limits are enforced and observable.
- The escape corpus runs in CI on disposable Linux infrastructure.
- The threat model and residual risks are published with the release.
- The isolation tier is recorded in the journal and shown to the user.

## 8. Verification

- Unit tests for policy, path validation, effect evaluation, and journal events.
- Integration tests for compile diagnostics, worker lifecycle, and resource limits.
- An escape corpus of non-destructive cases that must fail closed.
- Static analysis, CodeQL, dependency review, and secret scanning.
- Manual review for changes that touch policy, isolation, network, files, processes, secrets, or telemetry.
- Fuzzing of parsers and host boundaries as the surface grows.
- No release claim without evidence.

## 9. Residual risk statement

The v0.1 sandbox is a local, single-tenant, container-based boundary. It is not a hardened multi-tenant isolation service. It reduces risk; it does not eliminate it. A kernel or container-runtime vulnerability, a misconfigured host, a permissive operator policy, or a bug in the host contract can still cause harm.

The project will publish conservative claims, name the isolation tier, and document residual risk. It will not claim that generated code is "safe" in absolute terms.
