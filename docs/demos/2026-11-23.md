## Finding: compilation is not the isolation boundary

A file-based probe against .NET 10.0.12 shows where the entry points actually live:

```
System.Private.CoreLib      (typeof(object))
System.Private.CoreLib      (typeof(System.IO.File))
System.Diagnostics.Process  (typeof(System.Diagnostics.Process))
```

`System.IO.File` is in `System.Private.CoreLib`, so removing `System.IO` from the reference whitelist cannot prevent file access. The banned-namespace scan is defence-in-depth and a diagnostic aid only; real enforcement is the runtime isolation tier from ADR-0004. This is recorded in ADR-0006.

## Dependency added

`Microsoft.CodeAnalysis.CSharp` 5.12.0 — needed for the compile pipeline; MIT licence (Microsoft); runs on the host against untrusted source, so source size is capped and the compile step is scheduled to move behind the execution boundary. Review in ADR-0006.

## Execution spike (same day)

`Runesgalder.Sandbox.Worker` loads a compiled analysis assembly, reads a CSV table, calls `IAnalysis`, and writes a JSON result. The same worker binary runs on the host and inside a locked-down container.

```bash
dotnet test Runesgalder.sln -c Release --no-build
dotnet publish src/Runesgalder.Sandbox.Worker/Runesgalder.Sandbox.Worker.csproj -c Release -o artifacts/worker
docker build -f src/Runesgalder.Sandbox.Worker/Dockerfile -t runesgalder-worker:dev artifacts/worker
docker run --rm --network none --memory 256m --memory-swap 256m --cpus 1 --pids-limit 64 \
  --read-only --tmpfs /tmp:rw,size=16m --cap-drop ALL --security-opt no-new-privileges \
  -e DOTNET_EnableDiagnostics=0 -v "<job>:/work:ro" -v "<job>:/out:rw" \
  runesgalder-worker:dev --script /work/script.dll --data /work/data.csv \
  --out /out/result.json --timeout-ms 5000
```

### Results

- Tests: 24 passed, 0 failed (3 Flow, 21 sandbox, including 6 worker and 3 container-runner tests).
- Basic job (revenue by region, 3 rows): host, direct container, and runner produce the same result — `total=605`, one bar chart, one log line.
- Container analysis duration: 37–56 ms; host: 65 ms. Host compile latency: about 1.10 s in a cold process (Roslyn JIT plus reference load).
- Output quota: a script that logs 64 bytes with a 16-byte quota fails with `output-quota` and exit code 5.
- Cooperative timeout: a script that awaits with the supplied token fails with `timeout` and exit code 3 after the limit.
- Memory ceiling: a script that allocates 400 MiB under a 256 MiB limit fails with `OutOfMemoryException` and exit code 1; the container did not grow past its limit.
- Read failure and row limits are reported as `input` with exit code 2; contract mismatches as `contract` with exit code 4.

### Hard deadline

A script that calls `Thread.Sleep(60s)` ignores the cancellation token. The worker cannot stop it, so `Runesgalder.Sandbox.Containers.SandboxContainerRunner` owns the flags, the deadline, and cleanup:

- It passes `--name`, the policy limits, `--network none`, `--read-only`, a 16 MiB `/tmp`, `--cap-drop ALL`, and `no-new-privileges`.
- It waits for the policy timeout plus a five-second grace, then runs `docker kill` and `docker rm -f` on the container.
- The same slow job under a 1 s timeout was killed after about 6 s, reported `timedOut=true`, wrote no result, and left no container behind.

### Limits at this tier

- The worker handles one job and exits; script assemblies are loaded into a private `AssemblyLoadContext` but not unloaded.
- Compilation still happens on the host. Moving it inside the container is deferred; the source-size cap is the only compile bound today.
- Network isolation is asserted by the container flags and covered by an argument test; no script that is allowed to make a network call exists yet, because generated code cannot reference `System.Net`.
- The runner is not exercised by CI. It is verified by hand on this machine; CI covers argument construction only.
